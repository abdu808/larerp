# خطة تنفيذ مسار Reports, QA and DevOps

## الهدف والنطاق

يهدف هذا المسار إلى بناء طبقة التقارير والتحليلات وضبط الجودة والتشغيل المستمر لمشروع Laravel + Filament + PostgreSQL، بحيث تستطيع كل الموديولات إنتاج تقارير موحدة، قابلة للتصفية، والتصدير، والمراجعة، مع وجود مسار واضح للاختبارات، النشر، النسخ الاحتياطي، المراقبة، وإدارة الإصدارات.

هذا المسار لا ينشئ منطق أعمال خاص بالتبرعات أو الرعاية أو المالية أو الأرشفة، ولا يضيف كود Laravel في هذه الوثيقة. دوره هو تحديد الخطة التنفيذية، حدود الملكية، العقود المشتركة، ومعايير القبول التي يجب على فرق الموديولات الالتزام بها عند تسليم بياناتها للتقارير والتشغيل.

النطاق يشمل:

- report templates وتعريف أنواع التقارير وحقولها وفلاترها.
- generated reports ودورة حياة التقارير المنشأة.
- dashboard widgets داخل Filament.
- PDF وExcel export.
- تشغيل التقارير الثقيلة عبر queues.
- اختبارات التقارير، التصدير، الصلاحيات، والجودة.
- acceptance criteria لكل مرحلة.
- CI/CD وبيئات النشر.
- deployment وrollback وrelease process.
- branch strategy وقواعد الدمج.
- backups واستعادة البيانات.
- monitoring وalerts وlog management.
- نقاط التكامل مع كل الموديولات.

## الافتراضات

- قاعدة البيانات المعتمدة هي PostgreSQL في التطوير والاختبار والإنتاج.
- Filament هو مدخل الإدارة الرئيسي لكل موارد التقارير ولوحات المعلومات.
- Laravel queues مستخدمة للمهام الطويلة مثل توليد PDF وExcel والتقارير الدورية.
- الصلاحيات والأدوار تأتي من مسار Platform Foundation.
- سجلات التدقيق والأرشفة تأتي من مسار Governance and Archive.
- كل موديول مسؤول عن صحة بياناته وقواعده، ومسار التقارير مسؤول عن عرضها وتجميعها وتصديرها وفق عقود واضحة.
- لا يتم تنفيذ تقارير تعتمد على جداول غير مستقرة أو غير معتمدة من مالك الموديول.

## المبادئ العامة

- التقارير تقرأ البيانات ولا تغيرها، باستثناء تسجيل metadata عن طلب التقرير وحالة التوليد والتنزيل.
- كل تقرير يجب أن يمتلك مالكًا وظيفيًا، وصفًا، صلاحيات، وفلاتر مقبولة.
- أي تقرير ثقيل أو قابل للتصدير يجب أن يعمل عبر queue بدل الطلب المتزامن.
- كل widget في لوحة المعلومات يجب أن يكون سريعًا، محدود النطاق، وقابلًا للتخزين المؤقت.
- التصدير يجب أن يحترم صلاحيات المستخدم والفلاتر المعتمدة.
- لا يتم كشف بيانات حساسة في PDF أو Excel إلا إذا كان لدى المستخدم صلاحية صريحة.
- كل pipeline نشر يجب أن يمر بالاختبارات والتحليل الثابت قبل الوصول للإنتاج.
- النسخ الاحتياطي والاستعادة جزء من متطلبات القبول، وليس خطوة تشغيلية لاحقة.

## ملكية الملفات المتوقعة لاحقًا

هذه الوثيقة لا تنشئ الملفات التالية، لكنها تحدد ملكيتها المستقبلية عند التنفيذ:

- `app/Filament/Resources/ReportTemplateResource.php`: مسار Reports, QA and DevOps.
- `app/Filament/Resources/GeneratedReportResource.php`: مسار Reports, QA and DevOps.
- `app/Filament/Widgets/*ReportWidget.php`: مسار Reports, QA and DevOps بالتنسيق مع مالك بيانات كل widget.
- `app/Jobs/GenerateReportJob.php`: مسار Reports, QA and DevOps.
- `app/Exports/*`: مسار Reports, QA and DevOps عند وجود export عام، أو الموديول المختص عند وجود export خاص جدًا.
- `app/Reports/*`: مسار Reports, QA and DevOps للعقود المشتركة، وملفات خاصة بالموديولات عند الحاجة.
- `tests/Feature/Reports/*`: مسار Reports, QA and DevOps بالتعاون مع مالك الموديول.
- ملفات CI/CD: مسار Reports, QA and DevOps بالتنسيق مع Platform Foundation.

## مراحل التنفيذ

### 1. تحليل احتياجات التقارير والعقود المشتركة

المهام:

- حصر التقارير المطلوبة من كل موديول.
- تصنيف التقارير إلى تشغيلية، مالية، رقابية، إدارية، ولوحات مؤشرات.
- تحديد مالك كل تقرير، الجمهور المستهدف، وتكرار استخدامه.
- تعريف فلاتر موحدة مثل التاريخ، الفرع، الحالة، المستخدم، نوع العملية، والموديول.
- تعريف مستويات حساسية البيانات في التقارير.
- تحديد التقارير التي تحتاج PDF، Excel، أو كليهما.
- تحديد التقارير الفورية مقابل التقارير التي يجب توليدها في الخلفية.
- توثيق عقود البيانات التي يجب أن يوفرها كل موديول للتقارير.

مخرجات المرحلة:

- قائمة تقارير أولية مصنفة حسب الموديول.
- تعريف موحد لفلاتر التقارير.
- مصفوفة صلاحيات لعرض وتوليد وتصدير التقارير.
- قائمة dashboard widgets المطلوبة.
- قائمة تقارير عالية الكلفة يجب تشغيلها عبر queues.

معايير القبول:

- لكل تقرير اسم واضح ووصف ومالك وظيفي.
- لكل تقرير مصدر بيانات محدد وموديول مسؤول.
- لا يوجد تقرير يعتمد على استعلام مجهول أو غير مملوك.
- كل تقرير يملك قرارًا واضحًا حول PDF وExcel والqueue.

### 2. تصميم report templates

المهام:

- تعريف مفهوم report template كقالب يصف التقرير قبل توليده.
- تحديد الحقول الأساسية: الاسم، الكود، الوصف، الموديول، نوع التقرير، الحالة، الصلاحيات، الفلاتر، صيغ التصدير، وجدولة التشغيل.
- دعم قوالب ثابتة يعرّفها النظام وقوالب قابلة للتفعيل أو التعطيل من الإدارة.
- منع حذف قالب مستخدم في generated reports، والاكتفاء بتعطيله.
- تعريف version لكل قالب حتى يمكن تتبع التقارير المنشأة بإصدار القالب المستخدم.
- تحديد قواعد التحقق من الفلاتر قبل تشغيل التقرير.
- تحديد صلاحيات إدارة القوالب منفصلة عن صلاحيات توليد التقارير.

مخرجات المرحلة:

- نموذج بيانات مفاهيمي لقوالب التقارير.
- شاشة Filament مستقبلية لإدارة القوالب.
- قواعد صلاحيات لإدارة وتفعيل القوالب.
- تعريف versioning للقوالب.

معايير القبول:

- يمكن تمييز القالب النشط من المعطل.
- لا يمكن تشغيل قالب بدون فلاتر صالحة.
- لا يمكن لمستخدم إدارة قالب لا يملك صلاحيته.
- أي تغيير مؤثر في قالب التقرير ينتج version جديد أو يسجل في audit log.

### 3. تصميم generated reports

المهام:

- تعريف generated report كنتيجة تشغيل قالب تقرير بفلاتر ومستخدم وتوقيت محدد.
- تحديد الحالات: pending، processing، completed، failed، expired، cancelled.
- تخزين metadata: المستخدم، القالب، الفلاتر، الصيغة، مدة التنفيذ، عدد السجلات، حجم الملف، ورسالة الخطأ عند الفشل.
- تحديد سياسة انتهاء صلاحية الملفات المصدرة.
- توفير شاشة Filament لعرض التقارير المنشأة وتنزيلها وإعادة تشغيلها عند السماح.
- منع المستخدم من رؤية تقارير لم يولدها إلا إذا امتلك صلاحية إدارية.
- تسجيل كل عملية تنزيل في audit log عند وجود بيانات حساسة.

مخرجات المرحلة:

- دورة حياة واضحة للتقرير المنشأ.
- قواعد الوصول والتنزيل.
- سياسة retention للتقارير والملفات.
- رسائل خطأ مفهومة للمستخدمين الإداريين.

معايير القبول:

- كل تقرير منشأ يمكن تتبعه إلى قالب ومستخدم وفلاتر.
- فشل توليد التقرير لا يوقف queue worker ولا يخفي سبب الفشل عن المسؤول.
- لا يمكن تنزيل تقرير منتهي أو غير مصرح.
- التقارير الحساسة تسجل عمليات الإنشاء والتنزيل.

### 4. dashboard widgets في Filament

المهام:

- تحديد widgets مشتركة على مستوى النظام مثل إجمالي التبرعات، عدد المستفيدين النشطين، مؤشرات المخزون، أرصدة مالية مختصرة، وتنبيهات الحوكمة.
- تصميم widgets قابلة للتصفية حسب الفترة والفرع أو النطاق المتاح للمستخدم.
- استخدام cache قصير المدة للقراءات الثقيلة.
- منع تنفيذ استعلامات باهظة عند تحميل dashboard.
- اعتماد widgets مختلفة حسب الدور والصلاحية.
- ربط كل widget بمالك بيانات من الموديولات.
- تحديد حالة empty state وحالة error state لكل widget.

مخرجات المرحلة:

- قائمة widgets مع مصدر البيانات والمالك.
- قواعد cache وrefresh.
- سياسة عرض حسب الصلاحيات.
- معايير أداء لكل widget.

معايير القبول:

- تحميل لوحة Filament لا يعتمد على تقارير PDF أو Excel.
- كل widget يحترم صلاحيات المستخدم.
- وجود fallback واضح عند عدم توفر بيانات.
- لا يتجاوز كل widget حد الأداء المتفق عليه في بيئة الاختبار.

### 5. PDF وExcel export

المهام:

- اعتماد أنماط تصدير موحدة لكل التقارير.
- تحديد شكل رأس التقرير: اسم المؤسسة، اسم التقرير، الفترة، الفلاتر، المستخدم، وقت التوليد.
- دعم PDF للتقارير الرسمية القابلة للطباعة.
- دعم Excel للتقارير التحليلية والمراجعة التفصيلية.
- توحيد أسماء الملفات المصدرة.
- تطبيق تنسيق عربي مناسب واتجاه RTL في PDF عند الحاجة.
- حماية البيانات الحساسة بإخفاء أو تقليل الحقول حسب الصلاحية.
- منع التصدير المتزامن للتقارير الكبيرة.
- تحديد حدود عدد السجلات للتصدير الفوري، وتحويل ما يتجاوزها إلى queue.

مخرجات المرحلة:

- معيار موحد لترويسة واسم ملفات التصدير.
- قواعد اختيار PDF أو Excel.
- حدود حجم ومدة التصدير.
- قواعد إخفاء البيانات الحساسة.

معايير القبول:

- PDF قابل للقراءة والطباعة ويعرض الفلاتر المستخدمة.
- Excel يحتوي أعمدة واضحة وأنواع بيانات مناسبة.
- الملفات المصدرة لا تكشف حقولًا خارج صلاحيات المستخدم.
- التقارير الكبيرة تعمل في الخلفية وتظهر حالتها للمستخدم.

### 6. queues وتشغيل المهام الخلفية

المهام:

- تحديد queue مخصصة للتقارير الثقيلة.
- فصل queues الحرجة عن queues التقارير إذا كان المشروع يستخدم مهام تشغيلية أخرى.
- ضبط retry وtimeout حسب نوع التقرير.
- تسجيل failure metadata بشكل قابل للتشخيص.
- منع تكرار تشغيل نفس التقرير بنفس الفلاتر عند وجود تقرير حديث صالح، إذا كان ذلك مناسبًا.
- إضافة آلية rate limiting لتوليد التقارير حسب المستخدم أو الدور.
- تحديد مراقبة queue workers في الإنتاج.

مخرجات المرحلة:

- سياسة تشغيل queues للتقارير.
- حدود timeout وretry.
- قواعد منع الضغط الزائد.
- آلية متابعة فشل jobs.

معايير القبول:

- فشل job واحد لا يؤثر على باقي jobs.
- يمكن للمسؤول معرفة سبب فشل التقرير.
- لا يستطيع مستخدم واحد إغراق queue بطلبات متكررة.
- queue workers مراقبة ويصدر تنبيه عند توقفها.

### 7. اختبارات التقارير والجودة

المهام:

- كتابة اختبارات feature لصلاحيات عرض القوالب والتقارير المنشأة.
- كتابة اختبارات لفلاتر التقارير الأساسية.
- كتابة اختبارات للتصدير PDF وExcel على مستوى وجود الملف وصحة metadata الأساسية.
- كتابة اختبارات queue للتأكد من انتقال الحالة من pending إلى completed أو failed.
- كتابة اختبارات widgets للأدوار المختلفة.
- إضافة factories أو seed data محدودة للتقارير دون الاعتماد على بيانات إنتاج.
- اعتماد static analysis وformatting ضمن pipeline.
- منع flaky tests عبر تثبيت الوقت واستخدام بيانات اختبار واضحة.

مخرجات المرحلة:

- test matrix للتقارير حسب الموديول.
- اختبارات صلاحيات وتصدير وqueues.
- قواعد جودة للكود المستقبلي.
- بيانات اختبار محدودة ومعزولة.

معايير القبول:

- كل تقرير أساسي لديه اختبار واحد على الأقل للفلاتر والصلاحيات.
- كل export أساسي لديه اختبار نجاح واختبار رفض صلاحية.
- CI يفشل عند كسر اختبارات التقارير.
- لا تعتمد الاختبارات على ترتيب غير مضمون أو تاريخ النظام الحقيقي.

### 8. CI/CD

المهام:

- تعريف pipeline موحد للفرع develop وفروع الميزات وطلبات الدمج.
- تشغيل install dependencies وlint وstatic analysis وtests.
- تشغيل اختبارات PostgreSQL داخل CI بدل SQLite عند اختبار سلوك قاعدة البيانات.
- التحقق من migrations قبل الدمج.
- إنتاج artifact أو build قابل للنشر حسب بنية المشروع.
- منع الدمج عند فشل الاختبارات أو التحليل الثابت.
- إضافة خطوات security checks للأسرار والحزم عند الإمكان.
- فصل pipeline الاختبار عن pipeline النشر.

مخرجات المرحلة:

- Pipeline لطلبات الدمج.
- Pipeline للنشر إلى staging.
- Pipeline للنشر إلى production بموافقة يدوية.
- توثيق متغيرات البيئة المطلوبة.

معايير القبول:

- لا يتم دمج PR إلى develop دون CI ناجح.
- staging يتحدث من develop أو release branch حسب استراتيجية الإصدار.
- production لا يحدث دون approval واضح.
- الأسرار لا تحفظ داخل المستودع.

### 9. deployment وبيئات التشغيل

المهام:

- تعريف البيئات: local، testing، staging، production.
- توثيق متغيرات البيئة المطلوبة للتطبيق، قاعدة البيانات، queue، mail، storage، والmonitoring.
- تحديد خطوات النشر: سحب الإصدار، تثبيت الاعتمادات، بناء assets، تشغيل migrations، إعادة تحميل الخدمات، وتشغيل health checks.
- تحديد سياسة تشغيل migrations في الإنتاج.
- تجهيز rollback plan عند فشل النشر.
- التأكد من تشغيل queue workers وscheduler بعد النشر.
- تحديد صلاحيات ملفات التخزين والlogs.

مخرجات المرحلة:

- Runbook نشر واضح.
- قائمة متغيرات البيئة.
- Health checks بعد النشر.
- Rollback checklist.

معايير القبول:

- يمكن نشر staging بخطوات موثقة وقابلة للتكرار.
- production deployment يحتوي نقطة موافقة وrollback.
- queue workers وscheduler يعملان بعد النشر.
- health check يؤكد اتصال التطبيق بقاعدة البيانات والcache والqueue.

### 10. backups واستعادة البيانات

المهام:

- تحديد سياسة نسخ احتياطي PostgreSQL يومية وأسبوعية.
- تحديد retention حسب المتطلبات التشغيلية والتنظيمية.
- نسخ ملفات storage المهمة التي تحتوي exports أو مرفقات معتمدة.
- تشفير النسخ الاحتياطية عند التخزين الخارجي.
- اختبار restore دوري في بيئة معزولة.
- توثيق RPO وRTO المقبولين.
- منع الاعتماد على backup غير مختبر.

مخرجات المرحلة:

- Backup policy.
- Restore runbook.
- جدول اختبار الاستعادة.
- سجل آخر نسخ واستعادة ناجحة.

معايير القبول:

- توجد نسخة احتياطية مجدولة لقاعدة البيانات.
- توجد آلية تحقق من نجاح النسخ.
- تم اختبار restore بنجاح قبل الإطلاق.
- يعرف الفريق مدة فقد البيانات المقبولة ومدة الاستعادة المتوقعة.

### 11. monitoring وalerts

المهام:

- مراقبة أخطاء Laravel وHTTP 5xx.
- مراقبة queue length وfailed jobs.
- مراقبة زمن توليد التقارير.
- مراقبة مساحة التخزين المستخدمة لملفات التصدير والنسخ الاحتياطية.
- مراقبة اتصال PostgreSQL واستهلاك الموارد.
- مراقبة scheduler والتأكد من تنفيذ المهام الدورية.
- تعريف alerts للانقطاعات والفشل المتكرر.
- إضافة correlation id أو request id عند الحاجة لتتبع الأخطاء.

مخرجات المرحلة:

- Monitoring dashboard للتطبيق.
- Alerts للqueue وerrors وstorage وdatabase.
- Runbook للاستجابة للحوادث.
- سجل للحوادث والإجراءات التصحيحية.

معايير القبول:

- يتم تنبيه الفريق عند توقف queue worker.
- يتم تنبيه الفريق عند تكرر فشل توليد التقارير.
- يمكن تتبع خطأ تقرير من واجهة المستخدم إلى log الخادم.
- توجد مؤشرات واضحة لصحة التطبيق بعد النشر.

### 12. release process

المهام:

- تعريف أنواع الإصدارات: patch، minor، major أو ما يعادلها تشغيليًا.
- اعتماد changelog مختصر لكل إصدار.
- توثيق migrations المؤثرة وخطوات ما بعد النشر.
- تجهيز release checklist قبل production.
- تشغيل smoke tests بعد النشر.
- تحديد نافذة نشر عند وجود تغييرات مؤثرة.
- ربط كل إصدار بتذاكر أو مهام واضحة.

مخرجات المرحلة:

- Release checklist.
- Changelog template.
- Smoke test checklist.
- Rollback decision points.

معايير القبول:

- لا يتم إطلاق إصدار دون changelog.
- كل إصدار production قابل للتتبع إلى commit أو tag.
- توجد نتيجة smoke tests بعد النشر.
- يعرف الفريق متى يستمر ومتى ينفذ rollback.

### 13. branch strategy

المهام:

- اعتماد develop كفرع تكامل يومي.
- إنشاء feature branches من develop لكل مهمة أو تقرير.
- إنشاء release branches عند التحضير لإصدار مستقر.
- استخدام hotfix branches للإصلاحات العاجلة من production عند الحاجة.
- منع الدفع المباشر إلى develop وproduction branches إذا أمكن.
- اشتراط مراجعة PR من مالك المسار أو مالك الموديول المتأثر.
- إبقاء تغييرات التقارير منفصلة عن تغييرات منطق الأعمال قدر الإمكان.

الاقتراح:

- `feature/reports-<short-name>` لتطوير تقارير أو widgets.
- `feature/qa-<short-name>` لتحسينات الاختبارات والجودة.
- `feature/devops-<short-name>` لتغييرات CI/CD والتشغيل.
- `release/<version>` لتجهيز إصدار.
- `hotfix/<short-name>` للإصلاحات العاجلة.

معايير القبول:

- كل PR يوضح النطاق، الاختبارات، وأثره على التقارير أو النشر.
- أي تغيير يمس بيانات موديول يراجع من مالك ذلك الموديول.
- لا يتم خلط refactor واسع مع تقرير وظيفي في PR واحد.
- develop يبقى قابلًا للتشغيل والاختبار.

## نقاط التكامل مع الموديولات

### Platform Foundation

- استخدام نظام المستخدمين والصلاحيات والأدوار.
- استخدام إعدادات المؤسسة العامة في ترويسة التقارير.
- الاعتماد على timezone وlocale الموحدين.
- التنسيق مع foundation في ملفات CI الأساسية وبيئة PostgreSQL.
- استخدام audit hooks المشتركة عند توفرها.

### Social Care

- تقارير المستفيدين حسب الحالة، النوع، المنطقة، أو البرنامج.
- تقارير المساعدات والخدمات المقدمة للمستفيدين.
- widgets مثل عدد الحالات النشطة، الحالات الجديدة، والحالات التي تحتاج مراجعة.
- احترام حساسية بيانات المستفيدين وإخفاء الحقول الشخصية حسب الصلاحية.
- مراجعة مالك Social Care لأي تقرير يستخدم بيانات المستفيدين.

### Donations and Store

- تقارير التبرعات حسب الفترة، القناة، الحملة، المتبرع، والحالة.
- تقارير طلبات المتجر أو السلال أو المنتجات الخيرية إن وجدت.
- widgets مثل إجمالي التبرعات اليومية، الحملات الأعلى أداء، والطلبات المعلقة.
- تكامل مع queues للتقارير عالية الحجم.
- التأكد من عدم كشف بيانات دفع أو بيانات متبرعين حساسة دون صلاحية.

### Finance and Inventory

- تقارير القيود أو الحركات المالية الملخصة حسب الفترة والحساب.
- تقارير المخزون: الرصيد، الحركات، الأصناف منخفضة الكمية، وقيمة المخزون.
- widgets مثل الرصيد المالي المختصر، الالتزامات المفتوحة، وتنبيهات المخزون.
- مطابقة التقارير المالية مع قواعد الاعتماد والإقفال المالي التي يحددها مالك الموديول.
- منع تعديل التقارير المالية بعد التوليد إلا بإعادة توليد موثقة.

### Governance and Archive

- تقارير audit logs والأنشطة الحساسة.
- تقارير الوثائق المؤرشفة وحالات الاعتماد.
- استخدام سياسات retention والأرشفة للتقارير المنشأة.
- تسجيل تنزيل التقارير الحساسة.
- دعم متطلبات المراجعة الداخلية والخارجية.

### Notifications and Integrations

- إرسال إشعار عند اكتمال تقرير طويل أو فشله إذا كان نظام الإشعارات متاحًا.
- دعم webhooks أو integrations مستقبلية دون ربط مباشر في المرحلة الأولى.
- عدم إرسال ملفات حساسة عبر قنوات غير آمنة.
- توحيد رسائل الفشل والنجاح للمستخدمين.

## قائمة التقارير الأولية المقترحة

- تقرير ملخص تنفيذي شهري يجمع مؤشرات التبرعات، المستفيدين، المالية، والمخزون.
- تقرير التبرعات حسب الفترة والحملة والقناة.
- تقرير المستفيدين النشطين والخدمات المقدمة.
- تقرير المخزون والحركات والأصناف منخفضة الكمية.
- تقرير مالي ملخص حسب الفترة والحساب أو التصنيف.
- تقرير التدقيق والأنشطة الحساسة.
- تقرير التقارير المنشأة وحالات الفشل والتنزيل.
- تقرير جودة البيانات: سجلات ناقصة، حالات غير مكتملة، أو قيود تحتاج مراجعة.

## مصفوفة الصلاحيات المقترحة

- `reports.templates.view`: عرض قوالب التقارير.
- `reports.templates.manage`: إنشاء وتعديل وتعطيل قوالب التقارير.
- `reports.generated.view-own`: عرض التقارير التي أنشأها المستخدم.
- `reports.generated.view-all`: عرض كل التقارير المنشأة.
- `reports.generate`: توليد تقرير.
- `reports.export.pdf`: تصدير PDF.
- `reports.export.excel`: تصدير Excel.
- `reports.sensitive.view`: عرض حقول حساسة داخل التقارير.
- `reports.dashboard.view`: عرض dashboard widgets.
- `devops.release.approve`: الموافقة على نشر production إذا تم تمثيلها داخل النظام.

## معايير القبول النهائية للمسار

- توجد وثائق واضحة للتقارير والقوالب والتصدير والqueues.
- كل تقرير معتمد لديه مالك، مصدر بيانات، فلاتر، صلاحيات، واختبارات.
- يمكن توليد التقارير الطويلة في الخلفية وتتبع حالتها.
- يمكن تصدير التقارير المعتمدة إلى PDF وExcel وفق الصلاحيات.
- dashboard widgets لا تكسر أداء لوحة Filament.
- CI يمنع الدمج عند فشل الاختبارات أو التحليل الأساسي.
- staging قابل للنشر بشكل متكرر.
- production له release process وموافقة وrollback.
- النسخ الاحتياطي مجدول ومختبر بالاستعادة.
- monitoring يغطي الأخطاء والqueues والdatabase والتخزين.
- نقاط التكامل مع كل الموديولات موثقة ومملوكة.

## مخاطر يجب إدارتها

- تضخم التقارير وتحولها إلى منطق أعمال مكرر خارج الموديولات.
- استعلامات dashboard الثقيلة التي تبطئ Filament.
- تصدير بيانات حساسة دون صلاحية مناسبة.
- اختلاف أرقام التقارير المالية عن مصدر الحقيقة في Finance.
- عدم اختبار restore رغم وجود backups.
- queue workers غير مراقبة في الإنتاج.
- دمج تغييرات DevOps مع تغييرات وظيفية كبيرة في PR واحد.

## ترتيب الأولويات المقترح

1. تثبيت عقود التقارير والصلاحيات ومصفوفة التكامل.
2. تصميم report templates وgenerated reports.
3. تنفيذ أول مجموعة تقارير بسيطة لكل موديول.
4. إضافة PDF وExcel export للتقارير المعتمدة.
5. نقل التقارير الثقيلة إلى queues.
6. إضافة dashboard widgets الأساسية.
7. توسيع الاختبارات وربطها بـ CI.
8. تجهيز staging deployment.
9. تفعيل backups وrestore test.
10. تفعيل monitoring وalerts.
11. اعتماد release process وbranch strategy.
