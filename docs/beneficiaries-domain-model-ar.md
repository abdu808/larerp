# وثيقة نموذج عمل قسم المستفيدين وإدارة الحالات

هذه الوثيقة هي المرجع التنفيذي الملزم لقسم المستفيدين في LarERP. لا يجوز تطوير شاشات أو جداول جديدة في هذا القسم خارج هذا التصور إلا بقرار معماري لاحق موثق.

## القرار القيادي

النموذج الحالي `Family`, `Beneficiary`, `SocialCase`, `SocialCaseNote`, `SocialCaseAttachment` هو أساس تقني أولي فقط، وليس نموذج عمل كافيا لجمعية خيرية أو تنموية.

النظام المستهدف يجب أن يكون نظام إدارة حالة واحتياج وتدخل ونتائج، وليس نظام جمع بيانات ومرفقات.

## مبدأ الفصل

يجب الفصل بين هذه المفاهيم:

| المفهوم | المعنى | لا يخلط مع |
|---|---|---|
| الأسرة | الوحدة المعيشية والاجتماعية | الطلب أو القرار |
| المستفيد | الفرد داخل الأسرة أو الفرد المستقل | الحالة أو الخدمة |
| طلب الخدمة | ما يطلبه المستفيد أو الموظف | التقييم النهائي |
| الحالة الاجتماعية | ملف حي للدراسة والمتابعة | طلب واحد فقط |
| الدراسة | رأي الباحث وتحليله | قرار اللجنة |
| التقييم | قياس منظم للاحتياج والأولوية | الملاحظة الحرة |
| القرار | اعتماد أو رفض رسمي | توصية الباحث |
| الخطة | ما نريد تغييره خلال مدة | صرف منفرد |
| التنفيذ | خدمة أو صرف فعلي | الاعتماد فقط |
| المتابعة | قياس ما حدث بعد التدخل | إغلاق تلقائي |

## دورة العمل المعتمدة

```text
طلب خدمة جديد
-> فرز أولي
-> إنشاء أو ربط ملف أسرة/مستفيد
-> دراسة اجتماعية
-> تقييم احتياج
-> توصية الباحث
-> مراجعة المشرف
-> قرار لجنة أو صاحب صلاحية
-> اعتماد خدمة أو صرف
-> تنفيذ الخدمة
-> متابعة وقياس نتيجة
-> إغلاق أو إعادة تقييم
```

## الأدوار التشغيلية

| الدور | مسؤوليته | ممنوع عليه |
|---|---|---|
| استقبال | تسجيل طلب أولي واستكمال النواقص | اعتماد نهائي أو رؤية تفاصيل حساسة غير لازمة |
| باحث اجتماعي | دراسة الحالة والتقييم والتوصية | الصرف أو قرار اللجنة |
| مشرف | مراجعة جودة الدراسة وتجهيزها للجنة | تجاوز القرار الرسمي منفردا |
| لجنة | اتخاذ القرار واعتماد الاستثناءات | تعديل بيانات المستفيد التشغيلية |
| مالية | تنفيذ الصرف المعتمد | رؤية التفاصيل الاجتماعية والطبية غير اللازمة |
| إدارة | مؤشرات واستثناءات بصلاحية | تصدير حساس بلا سبب وصلاحية |
| مراجعة | تدقيق وامتثال | تعديل أو اعتماد أو صرف |

## حالات طلب الخدمة

`AssistanceRequest` يجب أن يمثل مدخل الرحلة، لا أن يحل محل الحالة الاجتماعية.

الحالات الأساسية:

- `draft`: مسودة
- `submitted`: مقدم
- `screening`: تحت الفرز
- `needs_information`: يحتاج استكمال
- `rejected_initially`: مرفوض أوليا
- `assigned_to_researcher`: محال لباحث
- `under_study`: تحت الدراسة
- `pending_supervisor_review`: بانتظار مراجعة المشرف
- `pending_committee`: بانتظار اللجنة
- `approved`: معتمد
- `approved_with_changes`: معتمد بتعديل
- `rejected`: مرفوض
- `pending_delivery`: بانتظار التنفيذ
- `delivered`: منفذ
- `under_follow_up`: تحت المتابعة
- `closed`: مغلق
- `cancelled`: ملغى

## حالات الحالة الاجتماعية

`SocialCase` هو محور إدارة الحالة الحية.

الحالات الأساسية:

- `new`
- `assigned`
- `assessment_in_progress`
- `pending_visit`
- `pending_documents`
- `ready_for_committee`
- `active_support`
- `monitoring`
- `suspended`
- `closed`
- `reopened`

## الموديلات المعتمدة للتنفيذ المرحلي

### المرحلة P0: أساس التشغيل

| الموديل | الغرض |
|---|---|
| `AssistanceRequest` | طلب خدمة رسمي مرتبط بأسرة أو مستفيد أو حالة |
| `BeneficiaryDocument` | مرفقات مصنفة لها تحقق وانتهاء وسرية |
| `CaseTimelineEntry` | سجل زمني واضح للطلب والحالة |

### المرحلة P1: الدراسة والقرار

| الموديل | الغرض |
|---|---|
| `CaseStudy` | دراسة الباحث وتوصيته |
| `NeedsAssessment` | تقييم احتياج بالنقاط |
| `FieldVisit` | زيارة ميدانية أو اتصال تحقق |
| `CommitteeDecision` | قرار رسمي مستقل مع سبب ومبلغ/خدمة |

### المرحلة P2: الخطة والتنفيذ

| الموديل | الغرض |
|---|---|
| `SupportPlan` | خطة دعم إغاثية أو تنموية |
| `ServiceDelivery` | تنفيذ خدمة أو صرف عيني/مالي |
| `FollowUp` | متابعة ونتيجة بعد التدخل |

## حقول أول زيارة

أول زيارة يجب أن تكون خفيفة ولا تتجاوز 3 إلى 5 دقائق.

الحد الأدنى:

- الاسم
- رقم الهوية أو الإقامة إن وجد
- رقم الجوال
- المدينة والحي
- نوع الطلب
- درجة العجلة
- وصف مختصر
- مصدر الطلب
- موافقة على حفظ البيانات
- المرفقات المتوفرة فقط

لا يطلب في أول زيارة:

- تفاصيل دخل كل فرد
- كل تفاصيل السكن
- دراسة اجتماعية كاملة
- تقييم نقاط
- قرار أو توصية
- بيانات بنكية إلا إذا أصبح هناك صرف معتمد

## تقييم الاحتياج MVP

يبدأ التقييم من 100 نقطة، ويكون قابلا للتطوير لاحقا.

| البعد | الوزن |
|---|---:|
| الدخل | 25 |
| هشاشة الأسرة | 20 |
| السكن | 15 |
| الصحة | 15 |
| التعليم | 10 |
| الديون والالتزامات | 10 |
| مصادر الدعم الأخرى | 5 |

النتيجة المقترحة:

- 0-30: احتياج منخفض
- 31-60: احتياج متوسط
- 61-80: احتياج عال
- 81-100: احتياج حرج

يحق للباحث التوصية، ولا يحق له تحويل النتيجة إلى قرار نهائي. يحق للجنة تعديل الأولوية مع سبب موثق.

## الوثائق والمرفقات

كل وثيقة يجب أن تحمل:

- نوع الوثيقة
- مستوى السرية
- حالة التحقق
- تاريخ الإصدار
- تاريخ الانتهاء
- من رفعها
- من تحقق منها
- سبب الرفض إن رفضت
- هل استخدمت في قرار

الحالات:

- `uploaded`
- `under_review`
- `verified`
- `rejected`
- `expired`
- `replaced`

لا يجوز حذف وثيقة استخدمت في قرار. تستخدم الحالة `replaced` أو أرشفة منطقية.

## الحوكمة والخصوصية

بيانات المستفيدين حساسة. يجب تطبيق الآتي:

- إخفاء جزئي للهوية والجوال وIBAN في الشاشات العامة.
- تسجيل فتح المرفقات الحساسة في `AuditLog` لاحقا.
- منع المالية من رؤية الدراسة الاجتماعية والتقارير الطبية.
- منع اللجنة من رؤية الوثائق الخام افتراضيا إلا عند الحاجة.
- منع التصدير الجماعي إلا بصلاحية مستقلة.
- حفظ سبب أي استثناء أو تجاوز.
- عدم تخزين القيم الحساسة كاملة في سجل التدقيق.

## قواعد منع التكرار

يجب فحص التكرار عند:

- إنشاء طلب جديد.
- إنشاء مستفيد.
- رفع مرفق.
- اعتماد دعم.
- تنفيذ صرف.

مؤشرات التطابق القوي:

- رقم الهوية
- رقم الجوال
- رقم الأسرة
- IBAN لاحقا

مؤشرات التشابه:

- اسم مشابه مع تاريخ ميلاد
- نفس العنوان
- نفس المرفق عبر hash لاحقا
- طلب مفتوح مشابه خلال فترة قريبة

## معايير قبول التنفيذ

لا يقبل أي عمل في قسم المستفيدين إلا إذا تحقق الآتي:

- كل موديل له migration وmodel وعلاقات أساسية واختبار.
- كل مورد Filament يستخدم حالات واضحة وbadges وفلاتر أساسية.
- لا توجد حقول حساسة ظاهرة بلا ضرورة.
- لا توجد قرارات مخزنة كنص حر فقط.
- لا توجد مرفقات بلا نوع وحالة تحقق.
- الاختبارات تمر بالكامل.
- `pint --test` ينجح.
- `migrate:fresh --seed` ينجح.
- لا يتم كسر الموارد الموجودة.

## ترتيب التنفيذ

1. تنفيذ `AssistanceRequest` و`BeneficiaryDocument`.
2. تنفيذ `CaseStudy`, `NeedsAssessment`, `FieldVisit`.
3. تنفيذ `CommitteeDecision` وربطه بالطلب والحالة.
4. تنفيذ `SupportPlan`, `ServiceDelivery`, `FollowUp`.
5. بناء لوحة تشغيل وقوائم انتظار.
6. تحسين ملف الأسرة/المستفيد إلى شاشة 360.
