# الوثيقة المرجعية لبناء منصة ERP للجمعيات

الإصدار: 0.1  
الحالة: مسودة تأسيسية قابلة للمراجعة  
الغرض: تحويل المشروع الحالي ومتطلبات العميل ورؤيتنا المستقبلية إلى مرجع واحد يمكن أن يعمل عليه أكثر من مطور أو وكيل AI بدون تداخل.

---

## 1. القرار التنفيذي

المنتج المقترح هو منصة ERP للجمعيات الخيرية والتخصصية، تبنى من جديد بأساس نظيف باستخدام Laravel و PostgreSQL، مع الاستفادة من المشروع الحالي كمرجع وظيفي وتحليلي وليس ككود يتم ترحيله حرفيا.

النظام لا يبنى كـ SaaS مشترك بقاعدة بيانات واحدة لكل الجمعيات. القرار المعتمد هو:

**Productized Single-Tenant**

أي أن لكل جمعية نسخة مستقلة من النظام:

- تطبيق مستقل أو حاوية مستقلة.
- قاعدة بيانات مستقلة.
- تخزين ملفات مستقل.
- إعدادات وهوية بصرية مستقلة.
- دومين أو سب دومين مستقل.
- مفاتيح دفع ورسائل مستقلة.

لكن الكود الأساسي يبقى موحدا في مستودع GitHub واحد، ويتم نشره لكل جمعية حسب إعداداتها.

## 2. مصادر التحليل

تعتمد هذه الوثيقة على ثلاثة مصادر:

1. المشروع الحالي المبني بـ React/Vite و Supabase.
2. وثيقة العميل التي تقترح نظام ERP ومتجر تبرعات للجمعيات.
3. رؤيتنا المستقبلية لبناء منتج قابل للبيع والتخصيص لأكثر من جمعية.

الهدف ليس اتباع مصدر واحد حرفيا، بل إنتاج نموذج نهائي متوازن:

- يحافظ على أفضل أفكار المشروع الحالي.
- يغطي متطلبات العميل العملية.
- يبنى على أساس تقني أنظف يصلح للتطوير الطويل.

---

## 3. لماذا لا ننقل المشروع الحالي كما هو؟

المشروع الحالي مفيد جدا كمرحلة Prototype، وفيه وحدات كثيرة تساعدنا على فهم المجال:

- المستفيدون والأسر.
- طلبات الإعانة.
- الكفالات.
- المالية.
- المخزون.
- الموارد البشرية.
- الزيارات الميدانية.
- الحوكمة والمجلس.
- الوثائق.
- التقارير والذكاء.

لكن لا ينصح ببنائه كمنتج نهائي للأسباب التالية:

- وجود تشويه في بعض النصوص العربية داخل الواجهة والوثائق.
- وجود أخطاء TypeScript تحتاج إصلاح.
- وجود تكرار في هيكل الملفات بين `src/` ومجلدات الجذر.
- كثرة ملفات SQL والإصلاحات الطارئة تجعل قاعدة البيانات صعبة الاعتماد كمرجع نهائي.
- بنية Supabase الحالية مناسبة للنموذج، لكنها أقل ملاءمة لمنتج Laravel إداري طويل العمر حسب توجهنا الجديد.
- متطلبات المتجر والتبرعات والدفع والشفافية ليست مكتملة كمنتج نهائي.

بناء على ذلك:

**يستخدم المشروع الحالي كمرجع وظيفي وشاشات وتجربة مجال، ولا يتم ترحيله ملفا بملف.**

## 4. التقنية المعتمدة للنسخة الجديدة

### 4.1 Backend

- Laravel 12 أو أحدث إصدار مستقر عند بدء التنفيذ.
- PostgreSQL كقاعدة بيانات رئيسية.
- Laravel Queues للمهام الثقيلة.
- Laravel Scheduler للمهام الدورية.
- Laravel Policies و Gates للصلاحيات.
- Spatie Permission لإدارة الأدوار والصلاحيات.
- Laravel Excel للاستيراد والتصدير.
- نظام Media Library أو بديل منظم لإدارة المرفقات.

### 4.2 Admin Panel

- Filament للوحة الإدارة الداخلية.
- كل موديول له Resources و Pages و Widgets خاصة به.
- استخدام Policies مع كل Resource.
- عدم بناء لوحة إدارة يدوية إلا عند وجود حاجة واضحة.

### 4.3 Public Website and Store

- Laravel Blade + Livewire + Tailwind كبداية.
- واجهة عربية RTL.
- صفحة جمعية عامة.
- فرص تبرع.
- متجر خيري.
- صفحة مشروع أو حملة.
- دفع إلكتروني.
- إيصالات رقمية.

### 4.4 Deployment

- مستودع GitHub واحد للكود.
- لكل جمعية ملف بيئة مستقل.
- Docker اختياري في البداية، لكنه يفضل عند التوسع.
- PostgreSQL مستقل لكل جمعية.
- Storage مستقل لكل جمعية.
- نسخ احتياطي لكل جمعية بشكل منفصل.

## 7. مقارنة مبدئية بين المشروع الحالي والمشروع الجديد

| المجال | موجود في المشروع الحالي | ينقل كما هو؟ | القرار |
|---|---:|---:|---|
| المستفيدون | نعم | لا | يستفاد من المنطق والشاشات |
| البحث الاجتماعي | جزئي | لا | يعاد بناؤه كموديول مستقل |
| الطلبات | نعم | لا | يعاد تنظيم مسارات الاعتماد |
| الكفالات | نعم | لا | يستفاد من العلاقات والمنطق |
| المالية | نعم | لا | تبنى على Laravel/PostgreSQL بشكل محاسبي أوضح |
| المخزون | نعم | لا | ينقل كمفهوم مع تحسين قواعد الرصيد |
| HR | نعم | لا | يبنى كموديول قابل للتفعيل |
| الحوكمة | جزئي | لا | يوسع ليشمل الإفصاح والمخاطر والسياسات |
| المتجر | غير مكتمل | لا | يبنى من الصفر |
| التبرعات والدفع | جزئي | لا | يبنى من الصفر مع Payment Transactions |
| الموقع العام | غير مكتمل | لا | يبنى من الصفر |
| AI | نعم | لا | يؤجل أو يبنى كطبقة اختيارية |

## 8. قواعد تصميم قاعدة البيانات

هذه القواعد إلزامية لأي مطور يعمل على المشروع:

- كل جدول له `id` UUID أو BigInt حسب القرار النهائي قبل التنفيذ.
- كل جدول له `created_at` و `updated_at` حيث يلزم.
- الجداول الحساسة تضيف `created_by` و `updated_by` عند الحاجة.
- استخدام PostgreSQL enums أو lookup tables حسب مرونة المجال.
- لا تستخدم JSONB للحقل الأساسي إذا كان يحتاج بحثا أو تقارير متكررة.
- يسمح بـ JSONB للإعدادات أو بيانات مرنة غير حرجة.
- كل علاقة مهمة لها foreign key.
- كل حقل بحث متكرر له index مناسب.
- لا تبنى شاشة قبل اعتماد migration و model و policy.

## 10. تقسيم العمل على مطورين أو وكلاء AI

هذه الوثيقة مصممة ليتم تقسيمها إلى مسارات عمل مستقلة.

### 10.0 نموذج القيادة والتنفيذ المعتمد

النموذج المعتمد للتطوير هو:

**قائد تطوير مركزي + وكلاء متخصصون لكل موديول داخل نفس المشروع**

أي أن المشروع لا يدار كمشاريع منفصلة، ولا يترك لكل وكيل أو مطور أن يبني بطريقته الخاصة. يوجد قائد تطوير مركزي مسؤول عن:

- القرار المعماري العام.
- تصميم قاعدة البيانات والعلاقات الأساسية.
- معايير التسمية والكود.
- حدود الموديولات.
- مراجعة مخرجات الوكلاء.
- دمج الشغل النهائي.
- منع التداخل بين الملفات والجداول.
- الحفاظ على اتجاه المنتج وعدم انحرافه.

الوكلاء المتخصصون يعملون كمساعدين ضمن حدود واضحة:

- كل وكيل يستلم موديولا أو Workstream محددا.
- كل وكيل يلتزم بالوثيقة المرجعية ومصفوفة التنفيذ.
- لا يحق لأي وكيل تغيير قرارات Foundation أو قاعدة البيانات العامة بدون مراجعة.
- لا يعمل وكيلان على نفس الملفات أو الجداول إلا إذا قسمت الملكية مسبقا.
- الدمج النهائي يتم مركزيا بعد المراجعة.

الترتيب المعتمد:

1. يبنى Foundation أولا بواسطة القائد المركزي.
2. تثبت conventions الخاصة بـ Laravel و Filament و PostgreSQL.
3. توزع الموديولات بعد ذلك على وكلاء متخصصين.
4. كل وكيل يسلم تغييرات محددة وقابلة للمراجعة.
5. القائد المركزي يراجع، يعدل عند الحاجة، ثم يدمج.

هذا النموذج معتمد لأنه يقلل الفوضى، ويحافظ على وحدة المعمارية، ويسمح بالاستفادة من الوكلاء بدون أن يتحول المشروع إلى أجزاء متنافرة.

## 12. معايير القبول العامة

لا يعتبر النظام جاهزا للإطلاق إلا إذا تحقق الآتي:

- يمكن إنشاء جمعية أو نسخة تشغيل مستقلة.
- يمكن إنشاء مستخدمين وأدوار وصلاحيات.
- لا يرى المستخدم إلا ما تسمح به صلاحياته.
- يمكن إدارة مستفيد ودراسة حالة ومرفقات.
- يمكن إنشاء مشروع أو حملة.
- يمكن تسجيل تبرع وربطه بداعم ومشروع.
- يمكن إصدار إيصال.
- يمكن تسجيل مصروف وربطه بمشروع.
- يمكن استخراج تقارير أساسية.
- يوجد Audit Log للعمليات الحساسة.
- يوجد Backup مجرب.
- يوجد دليل نشر وتشغيل.
- لا توجد بيانات حساسة منشورة في الموقع العام.

## 13. ما يحتاج قرارا لاحقا

هذه النقاط لم تحسم نهائيا بعد:

- هل تكون الواجهة العامة Blade/Livewire فقط أم يوجد React لاحقا لبعض الأجزاء؟
- هل نبدأ بـ Docker من اليوم الأول أم بعد MVP؟
- ما بوابة الدفع المستهدفة أولا؟
- هل نستخدم UUID في كل الجداول أم BigInt مع UUID خارجي؟
- هل النظام يحتاج محاسبة كاملة أم مالية تشغيلية فقط في أول إصدار؟
- هل يتم بناء تطبيق جوال لاحقا أم نكتفي بواجهة متجاوبة؟

## 14. تعليمات استخدام الوثيقة مع مطورين أو وكلاء AI

عند تكليف أي مطور أو وكيل AI:

1. حدد له Workstream واحد فقط.
2. حدد الموديولات التي يملكها.
3. حدد الملفات أو المجلدات التي يحق له تعديلها.
4. امنعه من تغيير قرارات معمارية عامة بدون مراجعة.
5. اطلب منه تسليم:
   - migrations
   - models
   - policies
   - resources
   - tests
   - notes
6. لا تقبل أي موديول لا يحتوي على صلاحيات وقواعد قبول.

## 15. الخلاصة

المنتج الجديد يجب أن يبنى كنظام نظيف وطويل العمر، لا كترقيع للمشروع الحالي. المشروع الحالي قيمة كبيرة لأنه كشف المجال والاحتياجات والشاشات الممكنة، لكنه لا يكون مصدر الكود النهائي.

القرار المعتمد:

**Laravel + PostgreSQL + Filament + Productized Single-Tenant**

مع تقسيم العمل إلى مسارات واضحة تسمح بتطوير متوازي من أكثر من أربعة مطورين أو وكلاء AI.
