# الخلاصة القيادية لتقارير قادة الموديولات

تاريخ الخلاصة: 2026-05-07  
النطاق: مراجعة قادة موديولات LarERP بعد بناء MVP أولي للموديولات الأساسية.

## القرار العام

النظام الحالي مقبول كـ MVP داخلي منظم، وليس كنظام إنتاجي جاهز لبيانات جمعية حقيقية.

العمل السابق أعطانا قاعدة ممتازة:

- شاشات Filament موجودة.
- الجداول والعلاقات الأساسية موجودة.
- الاختبارات الحالية ناجحة.
- كل موديول له بداية واضحة.

لكن قادة الموديولات اتفقوا على أن الأولوية الآن ليست إضافة شاشات أكثر، بل تثبيت قواعد السلامة:

- منع الحذف الخطر.
- ضبط الصلاحيات.
- منع تعارض العلاقات.
- حماية السجلات المالية والاجتماعية.
- جعل الأرصدة ناتجة من حركات معتمدة، لا حقولا حرة.
- ربط سجل التدقيق بالأحداث الفعلية.

## أهم المخاطر المشتركة

### 1. الحذف المباشر

يوجد خطر في حذف سجلات لها أثر اجتماعي أو مالي أو تشغيلي.

القرار:

- لا نعتمد الحذف النهائي في الموديولات الحساسة.
- نستخدم SoftDeletes أو أرشفة تشغيلية.
- بعد وجود حركة أو اعتماد أو تبرع أو مرفق، يمنع الحذف أو يصبح بإجراء إداري خاص.

### 2. الصلاحيات العامة

الصلاحيات الحالية جيدة كبداية، لكنها واسعة في بعض الأماكن.

القرار:

- ننتقل من `*.manage` العامة إلى صلاحيات أدق تدريجيا.
- نحمي أدوار النظام مثل `Super Admin`.
- نمنع غير Super Admin من منح صلاحيات حساسة.
- نربط إعدادات الجمعية وسجل التدقيق بصلاحيات صريحة.

### 3. سجل التدقيق

يوجد جدول وسجل عرض، لكنه لا يسجل الأحداث فعليا بشكل شامل حتى الآن.

القرار:

- AuditLog يصبح مكونا مركزيا لكل العمليات الحساسة.
- نسجل تغييرات المستخدمين، الأدوار، الصلاحيات، إعدادات الجمعية، الحالات الاجتماعية، التبرعات، والحركات المالية/المخزنية.
- نخفي القيم الحساسة مثل كلمات المرور والبيانات الخاصة.

### 4. سلامة العلاقات

بعض العلاقات يمكن أن تقبل تعارضا من الواجهة أو التطبيق.

أمثلة:

- حالة اجتماعية مرتبطة بأسرة ومستفيد من أسرة أخرى.
- تبرع مرتبط بحملة لا تتبع المشروع المختار.

القرار:

- نضيف validation وقواعد Domain تمنع هذه التعارضات.
- نضيف اختبارات لكل تعارض مهم.

### 5. الأرصدة المالية والمخزنية

الأرصدة الحالية موجودة كحقول مباشرة. هذا مقبول كبداية، لكنه خطر إنتاجيا.

القرار:

- الرصيد المالي والمخزني لا يكون مصدر الحقيقة.
- مصدر الحقيقة هو حركة معتمدة أو قيد مرحل.
- الرصيد يكون محسوبا أو مجمعا وفق خدمة واضحة.

## ترتيب التنفيذ القادم

### المرحلة 1: حوكمة وأمان قبل التوسع

هذه المرحلة يجب أن تبدأ الآن لأنها تحمي كل ما بعدها.

المهام:

- ربط `OrganizationProfileResource` بصلاحيات `settings.view` و `settings.manage`.
- ربط `AuditLogResource` بصلاحية `audit_logs.view`.
- حماية `Super Admin` و `Admin` من الحذف أو التعديل الخاطئ.
- منع منح دور `Super Admin` إلا من Super Admin.
- إخفاء أو تثبيت `guard_name` في واجهات الأدوار والصلاحيات.
- إضافة أساس Audit service أو observers للأحداث الحساسة.
- إضافة اختبارات authorization لهذه الحالات.

### المرحلة 2: تثبيت موديول المستفيدين

هذا الموديول حساس لأنه يحتوي بيانات أسر وأفراد ومرفقات.

المهام:

- منع ربط حالة اجتماعية بمستفيد من أسرة مختلفة.
- استبدال الحذف النهائي بسياسة أرشفة أو SoftDeletes.
- إضافة باحث اجتماعي مسؤول عن الأسرة أو الحالة.
- إضافة فلاتر تشغيلية: الحالة، الأولوية، المدينة، الحي، تاريخ الفتح.
- تحويل الملاحظات والمرفقات إلى تجربة مرتبطة داخل صفحة الحالة.
- وضع سياسة مرفقات فعلية بدل `file_path` النصي.
- إضافة اختبارات للهوية، الجوال، التعارضات، الأرشفة، والصلاحيات.

### المرحلة 3: تثبيت التبرعات قبل الدفع العام

لا نفتح بوابة دفع أو متجر قبل ضبط نموذج التبرع.

المهام:

- منع تبرع بحملة لا تتبع المشروع.
- تعريف سياسة التبرع العام إذا لم يوجد مشروع أو حملة.
- جعل `collected_amount` ناتجا من التبرعات المدفوعة فقط.
- إضافة حالات دفع أوضح، أو فصل التبرع عن `payment_transactions`.
- إضافة فلاتر للمشروع، الحملة، الحالة، التاريخ، طريقة الدفع.
- إضافة Relation Managers للمشروع والحملة.
- منع تعديل مبلغ أو حالة دفع دون صلاحية حساسة.

### المرحلة 4: تثبيت المالية والمخزون

لا نبني محاسبة كاملة دفعة واحدة، لكن نمنع الانحراف من الآن.

المهام:

- منع تعديل الأرصدة يدويا بعد وجود حركات.
- منع استخدام حساب أو صنف غير نشط.
- ضبط حالات المصروف: مسودة، معتمد، مدفوع، ملغى.
- منع دفع مصروف غير معتمد.
- منع تعديل أو حذف مصروف مدفوع.
- منع صرف مخزني يسبب رصيدا سالبا.
- تحديد معنى `adjustment`: فرق تسوية أم كمية نهائية.
- لاحقا: بناء دفتر قيود ومستودعات ومراكز تكلفة.

## توزيع قادة التنفيذ القادم

نموذج العمل القادم يكون كالتالي:

- قائد الحوكمة والأمان يقود المرحلة 1 لأنها تؤثر على كل الموديولات.
- قائد المستفيدين يبدأ بعد تثبيت صلاحياته الأساسية.
- قائد التبرعات يبدأ بتثبيت الاتساق قبل أي متجر أو دفع.
- قائد المالية والمخزون يركز على منع فساد الأرصدة قبل المحاسبة الكاملة.

كل قائد يقدم:

- تصميم مصغر قبل التنفيذ.
- قائمة ملفات مملوكة.
- اختبارات قبول.
- تقرير بعد التنفيذ.

## قاعدة قبول جديدة

لا يقبل أي تطوير قادم إلا إذا تحقق التالي:

- لا توجد بيانات عربية مشوهة في الواجهة.
- لا توجد علاقة يمكن أن تربط سجلات متعارضة.
- لا يوجد حذف مباشر لسجل حساس.
- لا توجد صلاحية حساسة متاحة لدور غير مخصص.
- كل تغيير حساس يظهر في AuditLog أو توجد خطة واضحة لتسجيله.
- `php artisan migrate:fresh --seed` ينجح.
- `php artisan test` ينجح.
- `php vendor/bin/pint --test` ينجح.
- `npm run build` ينجح عند وجود تغيير واجهة أو assets.

## الخلاصة

الخطوة الصحيحة الآن ليست تسريع إضافة المزايا فقط. الخطوة الصحيحة هي تحويل الـ MVP إلى أساس منضبط.

أفضل بداية: مرحلة الحوكمة والأمان، لأنها ستمنع أن يبني كل موديول فوق صلاحيات وحذف وتدقيق غير مكتملة. بعدها ننتقل للمستفيدين ثم التبرعات ثم المالية والمخزون وفق الأولويات أعلاه.
